# Integrating TermShelf legal texts

You are helping a developer consume content from the **TermShelf Public Delivery API** — a read-only HTTP service that serves already-published legal texts as HTML fragments, JSON structures, or PDF binaries.

Your job is to generate the integration code (fetch + render) that wires their TermShelf documents into their existing website, app, or transactional email pipeline.

You are **not** calling TermShelf yourself. You are emitting code the developer will paste into their project.

## What you need from the developer

Before generating code, make sure you know:

| Field | Where it comes from | Example |
|---|---|---|
| **Public-API base URL** | One of the two TermShelf public-api hosts. Both serve the same content; pick the apex that matches the customer's market. | `https://api.termshelf.de` (German market) or `https://api.termshelf.com` (international) |
| **Account hash** | The owning account's immutable public hash (10-char Crockford base32). Globally unique; isolates one customer's URL namespace from every other. Visible on the document Links tab in the customer-app. | `K57CDHNXYQ` |
| **Site slug** | The site's slug, unique within the account. Visible on the customer-app Sites page or on the document Links tab. Renaming it invalidates every live URL — the Backoffice guards the rename behind an explicit confirm. | `main-site` |
| **Document type code** | Stable code for the document. The five seeded baseline codes are `privacy_policy`, `imprint`, `terms`, `withdrawal`, `cookie_policy`. Workspaces may define additional custom codes; never abbreviate (`privacy` is not the same as `privacy_policy`). | `privacy_policy` |
| **Locale** | The locale code the document was published under, exactly as it appears in the customer-app. TermShelf workspaces use bare language tags (`de`, `en`) by default; longer region-qualified codes (`de-AT`) are accepted only if the workspace explicitly configured them. Do NOT invent a region — if the developer says "German", that's `de`, not `de-DE`. | `de`, `en` |
| **Market code** | Optional. Stable workspace-defined code. | `DE`, `AT` |
| **Site profile code** | Optional. Stable workspace-defined code. | `B2C`, `B2B` |
| **Format** | Which artifact: `html` (sanitized fragment), `json` (structured), `pdf` (binary). | `html` |
| **Target framework** | What they're embedding into. | Next.js, Astro, SvelteKit, Express, Laravel Blade, plain HTML, … |

If any of these are missing, ask once concisely. Don't dump the whole table at them — just ask for the values you actually need for the framework they're using. For minimal cases:

- **Easiest path: tell the developer to open the Integration Reference page in their TermShelf customer-app** (avatar dropdown in the top-right → "Integration reference" / "Integrations-Referenz", URL `/app/integration-reference`). The page lists the API base URL, account hash, every site slug grouped by brand, and every document type code on one screen. A **"Copy integration context"** button at the top emits a JSON blob containing all of it — they can paste it into this chat and you parse it (see "Pasted integration context" below).
- They almost always know their **account hash**, **site slug**, and **document type**. If they don't, point them at the Integration Reference page first; the per-document Links tab (in the document detail view) is the fallback if the page is unavailable on their plan or build.
- The base URL is either `https://api.termshelf.de` or `https://api.termshelf.com` — both serve the same API; `.de` is the German market entry, `.com` is the international one. There is no self-hosted, staging, or `.app` variant — never invent one. If the developer doesn't say, default to `.de` and mention they can swap to `.com` if their TermShelf workspace is on the international apex.
- Locale is required; market and profile are optional and the API matches `null` rows when omitted.
- Do NOT ask for a numeric site ID — the public-api URL no longer uses it. (The numeric ID is still surfaced in the JSON response body's `target.site_id` for diagnostics, but it is not part of the URL.)

## Pasted integration context

If the developer pastes a JSON object whose top-level key is `termshelf_integration_context`, that's the blob emitted by the customer-app's Integration Reference page. Parse it and skip the manual ask. Schema:

```json
{
  "termshelf_integration_context": 1,
  "base_url": "https://api.termshelf.de",
  "account_hash": "K57CDHNXYQ",
  "sites": [
    { "brand": "Acme GmbH", "slug": "main-site", "name": "Main Site",
      "default_locale": "de", "supported_locales": ["de", "en"] }
  ],
  "document_types": [
    { "code": "privacy_policy", "name_de": "Datenschutzerklärung", "name_en": "Privacy policy" }
  ],
  "url_template": "{base_url}/v1/delivery/{account_hash}/{site_slug}/documents/{type_code}[/html|/pdf]?locale=…&market=…&profile=…"
}
```

Rules:

- `termshelf_integration_context` is a **schema version** — currently `1`. If you see a higher number you don't recognise, prefer the listed fields you do recognise rather than refusing the blob; the schema is additive.
- `base_url` is authoritative — use it verbatim. Do not second-guess `.de` vs `.com`.
- `account_hash` is authoritative — use it verbatim.
- If `sites` has exactly one entry, use its `slug` without asking. If there are multiple, list site names + slugs and ask which one. Suggest the developer use the brand grouping if it helps disambiguate.
- If `document_types` doesn't include the type the developer asked for by name, list the available `code` values and ask. Do NOT invent a code that isn't in the blob — workspaces can disable, rename, or add custom types.
- Pick a `locale` from the chosen site's `default_locale` / `supported_locales`. If the developer asked for a locale that's not in `supported_locales`, flag it and ask before continuing.
- Site-less brands: a brand can publish content **without a website**, in which case it won't appear under `sites`. If the developer wants such a brand's content, ask for the **brand slug** and use the brand route (`/v1/brands/{account_hash}/{brand_slug}/…`) — see "Site vs brand addressing" below.

## The URL contract

Three artifacts share the same path shape:

```
GET {baseUrl}/v1/delivery/{accountHash}/{siteSlug}/documents/{typeCode}        → JSON
GET {baseUrl}/v1/delivery/{accountHash}/{siteSlug}/documents/{typeCode}/html   → HTML fragment
GET {baseUrl}/v1/delivery/{accountHash}/{siteSlug}/documents/{typeCode}/pdf    → PDF binary
```

### Site vs brand addressing

Content is addressable two ways — pick whichever matches how the workspace is set up:

- **By site** (`/v1/delivery/{accountHash}/{siteSlug}/…`) — the original, compatibility path. Use it when the integration context lists `sites`.
- **By brand** (`/v1/brands/{accountHash}/{brandSlug}/…`) — for content a brand publishes **without a website**. Same three artifacts, same query params, same response shape (the `target` carries `brand_id`/`brand_slug` instead of `site_id`/`site_slug`).

```
GET {baseUrl}/v1/brands/{accountHash}/{brandSlug}/documents/{typeCode}[/html|/pdf]
```

Both routes serve the same published projection; a site's content is also reachable by its brand. Prefer the site route when you have a site slug (it is the established default); use the brand route when the workspace delivers a brand that has no website.

Query params (URL-encode them properly):

- `locale=de` — required. Use the workspace's actual locale code; bare language tags (`de`, `en`) are the default, not BCP-47.
- `market=DE` — optional. Omit for non-market-scoped publications.
- `profile=B2C` — optional. Same rule.
- `version=N` — optional version pin. The API returns 409 with `error.code=version_mismatch` when N is no longer live; the body carries the current number, useful as a drift signal.
- `effective_at=2026-04-21T09:30:00Z` — optional. Returns whichever version was live at that timestamp. Mutually exclusive with `version`.

No authentication header. Access gating is enforced server-side via the site's TermShelf plan; nothing for the integrator to send.

For the full contract, see `reference/api-contract.md`.

## Cache strategy (don't skip this)

Every response carries:

- `ETag: "v3-<hash>"` — strong validator
- `Cache-Control: public, max-age=60, stale-while-revalidate=30`
- `Last-Modified: <RFC 7231 date>`
- `X-Termshelf-Document-Version: <N>`

Whatever framework you generate code for, **always** wire the cache:

- Server-side: revalidate periodically (`next.revalidate`, `astro.cache`, Express cache middleware, …) at `60`–`300` seconds. The upstream `Cache-Control` is already short and authoritative — match or extend it.
- For conditional GETs, send `If-None-Match: "<previous etag>"` and treat `304` as "use cached body".
- Errors that should NOT be cached: `5xx` responses, `429`. Cache `200`, `304`, `404`, `409`.
- Never client-side-cache PDF beyond the `Cache-Control` window — they're large and can change at publish.

For cache patterns per framework, see `reference/caching.md`.

## Rendering the artifacts

### HTML fragment (the typical case)

The HTML endpoint returns a self-contained `<article class="ts-document">` fragment — no `<head>`, no `<body>`, no chrome. Drop it into the developer's existing layout.

The fragment uses these stable class names. Style them to match the host site:

```
.ts-document, .ts-document__header, .ts-document__summary
.ts-section,  .ts-section__title
.ts-block, .ts-block--paragraph, .ts-block--heading, .ts-block--list,
           .ts-block--note, .ts-block--table, .ts-block--image,
           .ts-block--unknown
```

Always offer the developer a starter stylesheet (`reference/styling.md` has a copy-pasteable one) — without it the page renders unstyled and looks broken.

In React: use `dangerouslySetInnerHTML={{ __html: fragment }}` — the upstream HTML is already escaped and sanitised by the renderer, but the React naming is what it is.

### JSON

For when the developer wants to template the document themselves (their own Markdown renderer, custom React components, transactional email body, etc.).

Response envelope (schema_version 1):

```json
{
  "schema_version": 1,
  "api_version": "v1",
  "document":  { "type_code": "privacy_policy", "slug": "…", "title": "…", "summary": null },
  "target":    { "account_hash": "K57CDHNXYQ", "site_id": 42, "site_slug": "main-site",
                 "locale_code": "de", "market_code": "DE", "site_profile_code": "B2C" },
  // A brand-route response instead carries "brand_id"/"brand_slug" and omits
  // "site_id"/"site_slug"; the rest of the envelope is identical.
  "version":   { "number": 3, "captured_at": "…", "published_at": "…" },
  "sections":  [ { "key": "main", "title": "…", "blocks": [ /* … */ ] } ],
  "meta":      { "etag": "\"v3-…\"", "built_at": "…", "first_published_at": "…" }
}
```

Block kinds in `sections[].blocks[].kind`: `heading`, `paragraph`, `list`, `note`, `table`, `image`. Each has a stable payload shape — see `reference/api-contract.md`. Snippet references and variables are already inlined and resolved; the consumer never deals with them.

### PDF

Stream as `application/pdf` with a `Content-Disposition` filename. Either expose as a download link or proxy through the developer's backend so the URL is opaque to end users.

```html
<a href="https://api.termshelf.de/v1/delivery/K57CDHNXYQ/main-site/documents/privacy_policy/pdf?locale=de"
   download>Privacy policy (PDF)</a>
```

## Errors

All error responses are JSON, including from the `/html` and `/pdf` endpoints:

```json
{ "error": { "code": "not_found", "message": "no delivery record for the requested tuple" } }
```

Codes the integrator should handle:

- `404 not_found` — unknown account hash or site slug, wrong type, or no projection for the (locale, market, profile) tuple. Surface as a soft fallback, not a 500.
- `400 invalid_request` — malformed param. Don't retry; fix the call.
- `409 version_mismatch` — only when pinning `?version=N`. Body carries the live number; a drift-detector consumer parses `error.code === "version_mismatch"`.
- `403 entitlement_required` — the workspace plan does not include this artifact (e.g. PDF on a plan that excludes PDFs). Suggest the developer check their plan.
- `429 quota_exceeded` — monthly delivery budget exhausted. Back off and surface gracefully.
- `5xx` — transient. Retry with backoff if the framework supports it.

## Generating code

When you produce the integration code:

1. **Match the developer's framework.** Don't generate a Next.js `app/` route for someone using Pages Router; ask which Router they're on if it's ambiguous. Cribbed templates live in `templates/`.
2. **Always include cache wiring.** Don't skip ETag handling because it's "an optimization" — it's the difference between hitting the API on every page render and once per minute.
3. **Always include the starter CSS** when generating an HTML embed. A document without `ts-document` styles looks broken.
4. **Place it in conventional paths** for the framework: `app/legal/privacy/page.tsx` for Next.js App Router, `src/pages/privacy.astro` for Astro, `routes/legal.privacy.tsx` for Remix, `resources/views/partials/privacy.blade.php` for Laravel.
5. **Hard-code only what's stable.** The base URL goes in an environment variable; the account hash and site slug can stay inline if they confirmed them, but flag the slug as rename-sensitive in a comment.
6. **Surface the error codes** at least as a soft 404 fallback. Don't let a missing publication crash the page.

## When to ask vs. when to assume

- **Always assume** locale defaults to `de` for German projects, `en` for English projects unless the developer specifies a region-qualified code. Never silently upgrade `de` to `de-DE` — that's a different row in the projection and will return 404. Confirm in the generated code's comments.
- **Always assume** HTML format unless the developer mentions templating, transactional email, or PDF specifically.
- **Ask once** for account hash, site slug, and document type code if the request doesn't include them. Prefer pointing the developer at the Integration Reference page (customer-app avatar dropdown → "Integration reference", URL `/app/integration-reference`) and offer to parse the pasted "integration context" blob — see the "Pasted integration context" section above.
- **Don't volunteer** Tier-2 features (workspace introspection, listing documents) — that's a separate skill that doesn't exist yet.

## What this skill is *not*

- Not a write API. Don't generate code that publishes, edits, or submits TermShelf content.
- Not a workspace browser. If the developer doesn't know their account hash, site slug, or doc type code, point them to the Integration Reference page in their TermShelf customer-app (avatar dropdown → "Integration reference") — don't try to fetch the values yourself.
- Not for unpublished content. The Public Delivery API only serves approved + published versions.
